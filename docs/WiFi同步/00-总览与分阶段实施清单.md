## 1. 要解决什么

当前这套 App 是**纯离线**的：

- 扫码记录只落本地 Room + `/sdcard/ZhuangGui/*.tsv`，**要人工拷文件**才能进电脑
- 装柜任务（柜号 / 计划数量 / 条码规则）要在 PDA 上**手工录入**

本方案加一条**局域网 WiFi 通道**，做到两件事：

| 方向 | 内容 | 价值 |
| --- | --- | --- |
| **下行（电脑 → PDA）** | 装柜任务：柜号 + 计划装柜数量 + 条码规则（前缀 + 4 个开关 + 流水号范围） | 现场不用手录规则，避免录错 |
| **上行（PDA → 电脑）** | 扫码记录（含软删除状态）+ 装柜会话汇总 | 不用再拷 TSV，电脑实时有数 |

**硬约束（必须满足）**

1. **纯局域网**，不依赖外网、不依赖任何云服务
2. **离线优先**：没网也必须能照常扫码，恢复网络后自动补传
3. **不改变现有扫码逻辑**（`ScanDecider` / 报警 / 语音 / 落盘一律不动）
4. **不能丢数据、不能重复计数**（上传幂等）
5. 现场是**工业 PDA（东集 CRUISE2 / Android 11）**，界面要为小屏、戴手套可点考虑

## 2. 为什么走 WiFi，不走蓝牙

| 项 | WiFi（本方案） | 蓝牙（不采用） |
| --- | --- | --- |
| 电脑当服务端 | ✅ FastAPI 起一个端口即可 | ❌ Windows 做 BLE 外设要 WinRT/C#；Python `bleak` 只能当中心设备 |
| 吞吐 | ✅ 几十 MB/分钟 | ❌ BLE 实测几 KB/s |
| 多人多机 | ✅ 一个服务端挂 N 台 PDA | ❌ 配对/重连失败率高 |
| 现场排障 | ✅ 浏览器/curl 就能验 | ❌ 需要蓝牙抓包 |
| 无路由器时 | ✅ 开热点即可（见 §5） | — |

结论：**只用 WiFi**。蓝牙仅在"完全无网络且只传几十字节"时才考虑，本方案不做。

## 4. 关键设计决策（改动前必读）

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 传输协议 | **HTTP/1.1 + JSON**，明文（局域网） | 最简单、最好排障；PDA 端只需 OkHttp |
| 鉴权 | 请求头 `X-Sync-Token`（PC 生成的随机串） | 局域网也不安全，一个头成本极低 |
| 配对方式 | **二维码**（PDA 用自己的扫码枪扫 PC 屏幕）+ 手输兜底 | 这个 App 本来就是扫码器，零额外开发 |
| 上行幂等 | 每条扫码记录带 **`uid`（UUID）**，服务端以其为唯一键 | 断网重试、重复提交都不会翻倍 |
| 上行游标 | 用 **`syncedAt IS NULL`** 取待传，成功后回写时间 | 不引入新队列表，改动最小 |
| 下行游标 | 服务端维护自增 `rev`，PDA 存 `lastTaskRev` | 标准增量同步，PDA 只需记住一个数 |
| 时间 | 传输统一 **ISO8601 带时区**（`2026-10-20T15:01:02.123+08:00`），落库仍用 epoch millis | Room 的 `Converters` 存 `Long`，不能破坏 |
| 下行落地 | 落到新表 `sync_inbox`，**不自动建** `load_containers` | 避免与现场手工装柜冲突；由人点「装载」才生效 |
| 依赖 | PDA 只加 **OkHttp** 一个库；不要 Retrofit/Gson/ZXing | 工业机要小、要稳；`org.json` 系统自带够用 |

## 5. 现场网络三种拓扑（都要能跑）

| 拓扑 | 说明 | PC 地址 |
| --- | --- | --- |
| **A. 同一路由器** | 最常见 | 路由器分配，建议在路由器上给 PC 做 **DHCP 保留**（固定 IP） |
| **B. Windows 移动热点** | 现场没路由器 | Windows 热点默认 **`192.168.137.1`**，非常稳定 |
| **C. PDA 开热点** | PC 连 PDA | PC 地址由 PDA 分配，需查 PC 的当前 IP |

> ⚠️ 排查第一条：**路由器若开了「AP 隔离」，手机与电脑互 ping 不通**，此时任何方案都连不上。
