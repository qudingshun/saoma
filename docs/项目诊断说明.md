## 二、P0｜建议立刻处理

### P0-1 跨端规则前缀校验不一致（含 `-`/`#` 的规则无法同步）

- **位置**：
  - App 允许：`importer/RuleSourceImporter.kt:53`（`Regex("[A-Za-z0-9#\\-]+")`）、`ui/screen/RulesScreen.kt:534,552`（输入框过滤同样允许 `-`/`#`）；
  - 电脑端拒绝：`docs/WiFi同步/pc-server/server.py` 的 `_save_rulelib`（约 :695）与 `_parse_rulelib_xlsx`(:840) 用 `re.fullmatch(r"[A-Z0-9]{1,64}", prefix)`。
- **现象与影响**：v1.9.2 起为真实机型 `HYW-T55`、`#9970` 增加了 `-`/`#` 支持。若 PDA 执行「上传本机规则库」，服务端会抛 422，**整个请求失败**；电脑网页 Excel 导入则把该行**静默丢弃**（`continue`，只留下型号）。当前 WiFi 同步默认下线（`AppConfig.SYNC_ENABLED=false`），所以现场未暴露；一旦恢复同步必然踩中，且与 275 条现成规则库的维护口径冲突。
- **建议修法**：两端统一为 `[A-Z0-9#\-]{1,64}`，并把 App 侧 `sanitizePrefix` 的字符集作为唯一契约来源；Excel 解析遇到非法前缀应报错提示而不是静默丢行。
- **验收**：用含 `HYW-T55`、`#9970` 的规则库从 PDA 上传 → 服务端返回 200 且规则条数一致；同一文件从电脑网页 Excel 上传 → 两条规则均保留；两端各补一条单测。
- **状态**：⬜

### P0-2 操作指南 V1.6 未入库，readme 已在引用

- **现象与影响**：仓库 clone / pull 之后 readme 中的当前版指南链接是断的，新机器或交接同事拿不到操作手册。同时工作区还有 4 个 md 修改未提交（`readme.md`、`开发计划与优化建议.md`、`版本与里程碑.md`、`现场验收清单.md`）。
- **建议修法**：把 V1.6 的 docx + pdf 随这批文档改动一起提交并推送，使 `HEAD == origin/main`；提交前确认 docx/pdf 未被 Excel/Word 占用导致文件锁。
- **验收**：`git ls-files docs/*V1.6*` 有两条输出；在一个新 clone 的目录里 readme 链接可正常打开。
- **状态**：⬜

### P0-3 存储可写状态缓存不失效，首页误报"正常"

- **位置**：`export/FileExporter.kt:134-147`（`primaryWritable()` 用 `primaryWritableCache` 永久缓存）、`:303-318`（`append()` 只在主目录成功时置 true，失败不复位）、`ui/screen/HomeScreen.kt:64-71`。
- **现象与影响**：缓存一旦赋值，进程生命周期内不再实测。现场中途关闭「所有文件访问」、存储写满、卡被卸载时，`append()` 已把记录写进 App 私有目录，但首页仍按旧缓存显示 OK，橙条不出现——操作工以为记录落在 `/sdcard/zhuanggui`，实际要手动导回。
- **建议修法**：`append()` 主目录失败时把 `primaryWritableCache` 置为 `false` 或 `null`；`storageStatus()` 改为带"允许复检"参数，回首页（`LifecycleResumeEffect`）时强制复检一次。
- **验收**：正常扫码后关闭「所有文件访问」，再扫一码 → 首页立即出现 FALLBACK 橙条，OpLog 记录主目录不可写原因；重新授权回首页 → 提示消失。
- **状态**：⬜

### P0-4 "重新导出"会覆盖主目录同名 TSV，且在主线程执行

- **位置**：`export/FileExporter.kt:539-560`，关键行 `:550` 为 `f.copyTo(target, overwrite = true)`；调用点 `ui/screen/HomeScreen.kt:124-125`（Compose `onClick` 内同步调用）。
- **现象与影响**：兜底目录与主目录按相同结构镜像。若同一柜号一部分记录落在主目录、一部分暂存，`exportFallbackToPrimary()` 会用暂存文件**整体覆盖**主目录文件，丢掉只在主目录的那部分。此外它在主线程遍历拷贝文件，文件多时可能 ANR。
- **建议修法**：改为按行合并（以 `(时间, 条码)` 去重）或先备份主目录文件再覆盖；调用点用 `rememberCoroutineScope { launch(Dispatchers.IO) { … } }`，完成后再刷新首页状态。
- **验收**：构造"主目录已有 A 行 + 暂存目录有 B 行"的同柜文件 → 点击重新导出后 A、B 两行都在，且文件数/条数与数据库一致；大批量文件下界面不卡。
- **状态**：⬜

### P0-5 `OpLog.flushSync()` 不排空队列，崩溃时最后几条日志必丢

- **位置**：`log/OpLog.kt:83-89`。实现为 `f.appendText("", Charsets.UTF_8)`（打开即关的空写），而日志实际由 `io` 单线程执行器异步追加（`:66-76`）。
- **现象与影响**：`ZhuangGuiApp.installCrashHandler()` 在崩溃时调用 `flushSync()`，但队列里尚未执行的"扫码/落盘"日志不会被刷出。留下的日志停在崩溃前若干条，恰恰缺了定位问题最需要的上下文。
- **建议修法**：用 `io.submit { }.get()` 等待队列排空后再返回（崩溃线程可短暂阻塞，可接受）；或在崩溃回调里绕过队列直接同步写文件。
- **验收**：在扫码路径人为抛异常 → 导出的操作日志中必须同时出现最后一条业务日志、`App 崩溃` 与 `崩溃栈`。
- **状态**：⬜

## 三、P1｜稳健性与数据一致性

### P1-6 每次启动全表读入 + 全量重写所有 TSV

- **位置**：`ZhuangGuiApp.kt:62-76`（`getAllRecords()` → `rebuildFromRecords()`）、`FileExporter.kt:520-532`。
- **现象与影响**：已拍板不做自动归档，数据量只增不减。每次冷启动都把 `scan_records` 全表读进内存，再按「日期+柜号」重写全部文件。后果：① 这正是"冷启动 4~7 秒"的主因，且会继续线性变慢；② 现场用 Excel/WPS 在 TSV 里加的备注或修正，会在下次启动被数据库内容覆盖；③ `files += 2`（`:528`）不反映真实写出的文件数，启动日志数字失真；④ 只重建主目录，不合并 fallback 暂存目录的记录。
- **建议修法**：改为只补缺失/损坏的文件，并引入增量水位（如 `lastRebuildAt`）；或把全量重建降级为手动入口（与电脑端 `/api/v1/rebuild-exports` 对齐）。统计改成按真实写出的文件计数。
- **验收**：连续启动 3 次，第 2/3 次无文件重写；手动修改某个 TSV 的备注后重启，备注保留；主目录 + 暂存目录均有记录时重建后不丢。
- **状态**：⬜

### P1-7 落盘缺 `fsync`，原子写回退路径不原子

- **位置**：`FileExporter.kt:281-297`（`appendTo()` 用 `FileOutputStream(file, true)` 追加后直接关闭）、`:256-272`（`writeAtomically()` 的 `Files.move` 失败回退 `tmp.copyTo(file, overwrite = true)`）。
- **现象与影响**：追加写没有 `FileDescriptor.sync()`，PDA 拔电池/突然断电可能丢失最后一枪的落盘内容（数据库有记录、启动重建可补，但现场直接拷文件时会发现缺行）。回退路径用 `copyTo(overwrite=true)` 时，注释承诺的"避免读到半截文件"不成立。
- **建议修法**：追加后显式 `flush()` + `fd.sync()`；回退路径改为"写临时文件 → `File.renameTo()`（同目录通常可用）→ 失败才 copy"，并记 OpLog 说明降级。
- **验收**：大量连续扫码时 kill -9 进程后重启，最后一条记录可从数据库重建到 TSV；OpLog 能看到降级路径提示。
- **状态**：⬜

### P1-8 TSV 字段未转义，外部广播可撑坏列结构

- **位置**：`FileExporter.kt:220-227`（`lineOf()` 直接拼接 `containerNo`/`barcode`/`operatorId`）。
- **现象与影响**：条码来自外部广播，内容不受控。若含 Tab 或换行，导出的 TSV 会从 5 列变成更多列/多出行；而独立阅读器 `tsv-reader/.../TsvParser.kt` 反而支持引号字段，读写两端能力不对称。柜号也已用 `safeName` 处理文件名非法字符，但内容未清洗。
- **建议修法**：写入前把字段中的 `\t`/`\n`/`\r` 替换为空格或按 TSV 规则加引号转义，并与 `TsvParser` 的解析规则保持一致；补一条单测覆盖含控制字符的条码。
- **验收**：扫入含 Tab 的模拟条码 → 导出文件每行仍为 5 列，App 内「TSV 原文」与独立阅读器都能正确显示。
- **状态**：⬜
