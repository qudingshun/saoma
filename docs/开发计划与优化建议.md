## 三、下一步优化建议（按优先级）

> 排序依据：现场收益 × 实施成本 × 风险。P0 = 建议下一版就做；P1 = 本轮内择机做；P2 = 排期/待现场反馈。

### P0｜现场刚需，建议下一阶段

**1. 电脑端「装柜汇总报表」** ⏸ **2026-10-26 拍板不做**
- 结论：不做报表；电脑端继续按 PDA 分目录保存 TSV，现场需要时直接打开文件核对。
- 原方案保留备查：按「日期 / 柜号 / PDA」汇总正常、串号、重复、超量、辅助、计划量、已扫量、操作员并导出 Excel。

**2. PDA 首页「今日看板」**（方案已出，待排期）
- 内容：今日柜数 / 正常件数 / 异常件数（串号+重复+超量）/ 辅助码 + 最近异常提示。
- 收益：班组早会上不用进记录页；异常件当场就能发现。
- 工作量：0.5~1 天（复用现有 DAO 聚合）。
- 验收：首页数字与记录页按日统计一致。
- 详细方案见 [`后续增强方案_看板_备份_自动化.md`](后续增强方案_看板_备份_自动化.md) 第二节。

**3. 电脑端数据自动备份**（方案已出，待排期）
- 内容：服务每日定时把 `data` 目录（含 sync.db、TSV、规则库备份）压成带日期的 zip，默认保留 30 天。
- 收益：硬盘故障 / 误删 / 误清空可恢复；多 PDA 场景数据量增长后价值更高。
- 工作量：0.5~1 天（后台线程 + SQLite 一致性备份 + 保留策略 + 写日志）。
- 验收：手动触发一次备份并还原到临时目录验证可用。
- 详细方案见 [`后续增强方案_看板_备份_自动化.md`](后续增强方案_看板_备份_自动化.md) 第三节。

**4. 规则库按 PDA 独立（多线体）** ⏸ **2026-10-26 拍板不做**
- 结论：规则库**所有 PDA 统一一份**，保持现状；不按产线/客户拆分。
- 现场若需要不同前缀，由规则库统一维护型号与规则，PDA 从同一份规则库选择。

### P1｜稳健性（本轮内择机）

**5. 端到端自动化回归**（方案已出，待排期）
- 现状：已有真机负载脚本（12 柜 / 871 枪、kill -9、断网补传）验证过，但未纳入仓库。
- 方案：把「模拟扫码广播 → 落盘 → 同步 → PC 分目录 → 改名 → 下载 ZIP」做成一条可重复执行的脚本 + 断言，纳入发布前检查。
- 验收：一条命令跑完，输出「计数/文件/目录/版本」四项一致。
- 详细方案见 [`后续增强方案_看板_备份_自动化.md`](后续增强方案_看板_备份_自动化.md) 第一节；预计 2~3 人天。

**6. 现场排障日志（App 内可导出）** ✅ 已完成（v1.10.1）
- 现状：异常只写 Logcat，现场拿不到。
- 已实现：首页「操作日志」入口；记录启动/存储状态、每枪扫码（来源/判定/落盘）、落盘失败原因、删除/撤回/恢复、规则导入导出、崩溃栈；App 内部 `files/logs/oplog_yyyyMMdd.log`（每天一个、2MB 轮转），一键导出到 `/sdcard/zhuanggui/日志/`。
- 验收：断网 / 拒授权 / 存储满三种场景都能看到可读原因（日志页可直接看，不用连电脑）。

**7. 跨 PDA 重复 / 串号检测**（多台同时扫同一柜）
- 现状：同柜重复判断只在 PDA 本机，PC 侧不参与；两台 PDA 扫同一码不会互相报重复。
- 方案：PC 在收到记录时按「柜号 + 条码」回查近期记录并把标记随下一次同步回传（需新增字段与状态机）。
- 风险：局域网延迟与离线场景下语义需先定义（建议只提示不拦截）。
- 工作量：2~3 天（需产品口径确认）。

**8. 电脑端设备运维增强**
- 内容：设备离线提醒、令牌一键轮换（所有 PDA 需重配对）、按 PDA 重置规则库 / 记录、审计日志（谁在何时改了规则库）。
- 工作量：1 天。

**9. 同步策略省电**
- 内容：仅在充电或指定时段同步；WiFi 断开自动重试退避；页面显示「上次成功同步时间」。
- 工作量：0.5 天（WorkManager 约束 + 退避）。

### P2｜中长期 / 待现场反馈

**10. 扫描设置页再增强**：读取本机开发者选项里的实际广播名 / 键值，与 App 预期值自动比对，直接给出「匹配 / 不匹配 + 正确值」，避免现场照抄错误。
**11. 冷启动优化**（见 2.1）。
**12. 条码长度 / 校验位增强**（GS1-128 括号、AI 校验位等）。
**13. 语音库扩充**：> 999 朗读优化、多语种、装柜完成语音模板。
**14. 界面可配置**：字号缩放档位、深色主题开关（当前固定浅色）。
**15. 规则库版本历史**：每次上传/导入生成一个 rev，可查看与回滚（电脑端已有 rev 递增，可加回滚 UI）。

## 四、工程规范（沿用，不变）

- **提交纪律**：一个条目 = 一次提交 = 一个版本；改动完成、构建通过、装机验证后再推送；推送后 `HEAD == origin/main`。
- **编码规范**：全部文本 UTF-8（无 BOM）+ LF（`.gitattributes` 锁 `eol=lf`），任何机器 clone/pull 与本地逐字节一致。
- **测试要求**：改动涉及判定 / 解析 / 同步的，必须补或更新单测；涉及 DB 的必须补迁移测试（`app/src/androidTest/.../MigrationTest.kt`）。
- **安装包规范**：release 签名包；交付包含 APP + 电脑端 + 指南 + 交付说明，并记录 SHA-256。
- **数据安全**：任何覆盖/清空前先备份（规则库导入前备份、覆盖电脑端规则库前备份、PD 文件夹改名自动迁移）。

## 五、风险与已知限制

| 风险 / 限制 | 影响 | 现状 |
| --- | --- | --- |
| 广播来源不可校验 | 任意 App 可伪造同名广播 | 已知限制：收到即用 + OpLog 留痕；v1.10.2 起扫码只认广播，800ms 同码去重，双开也不会两条 |
| 规则库为全局一份 | 多线体需不同前缀库时互相覆盖 | **2026-10-26 拍板保持统一，不做按 PDA 独立**；多线体共用一份规则库 |
| 同一柜多台 PDA | 记录分目录不合并，计数各算各的 | 现场约定一柜一机；**不做电脑端合并报表** |
| 共享配对令牌 | 丢一台设备需全量重配对 | 待做令牌轮换（P1-8） |
| 仪器化测试会卸载 App | 跑测试可能清空设备数据 | 已加 `leaveApksInstalledAfterRun=true`；跑前仍建议快照 |
| 电脑端单机单进程 | 服务被关 = 停止同步 | 扫码不受影响（本地先落盘，联网补传） |
