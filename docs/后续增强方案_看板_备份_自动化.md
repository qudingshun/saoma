> 编制日期：2026-10-26

## 一、端到端自动化测试方案

### 1.1 目标

把现在依赖人工的「装机 → 扫码 → 落盘 → 判定 → 删除/撤回 → 装柜完成 → 电脑端同步/分目录/ZIP」固化成一条可重复执行的回归链路，发布前一条命令跑完并输出明确结论。

### 1.2 测试分层

| 层级 | 内容 | 执行方式 | 现状 |
| --- | --- | --- | --- |
| L1 单元测试 | 判定、解析、导出、同步 JSON、结果列映射 | `gradlew testDebugUnitTest` | 已有 48 项 |
| L2 迁移测试 | v8→…→v16、v5→v16 全链 | `gradlew :app:connectedDebugAndroidTest` | 已有 8 项 |
| L3 PDA 本机端到端 | 模拟广播扫码 → 数据库 → TSV → 汇总 → 删除/恢复 | adb + PowerShell/Python | 待建 |
| L4 电脑端同步端到端 | 上传记录 → 多 PDA 分目录 → 改名 → 回收站 → 下载 ZIP | Python 脚本 + 测试服务 | 待建 |

### 1.3 L3：PDA 本机端到端

**测试数据隔离**

- 每次运行使用唯一柜号，例如 `E2E-20261026-001`，避免碰现场真实柜号。
- 固定测试操作员 `E2E`。
- 运行前记录 `/sdcard/zhuanggui` 文件清单与数据库计数，运行后对比增量。

**执行步骤**

1. 安装当前 release APK，记录版本号/版本代码。
2. 通过 adb 发送 OEM 广播：
   ```powershell
   adb shell am broadcast -a com.android.server.scannerservice.broadcast `
     --es scannerdata "E2E条码内容"
   ```
3. 等待 1~2 秒，读取当天柜号 TSV 与数据库。
4. 对以下场景逐条断言：
   - 正常扫码 3 条：计数 +3，TSV 3 行，结果列「正常」。
   - 同码再扫：报警「重复」，TSV 新增「异常」行。
   - 流水号越界：报警「串号」，TSV「异常」。
   - 超过计划数量：报警「超量」，TSV「异常」。
   - 辅助码：不计数，TSV 结果「辅助」。
   - 删除/撤回：活动文件与回收站文件同步变化。
   - 装柜完成：`装柜完成汇总.tsv` 追加 1 行，字段与界面计数一致。
   - 杀进程重开：不丢记录，能回到设置页。
   - 旧四列/六列 TSV：启动后重建为五列，记录数不变。
5. 输出 `e2e-report.json`：版本、柜号、各判定数量、文件路径、成功/失败项。

**关键断言**

- 界面计数 = 数据库计数 = TSV 行数（删除/辅助按口径扣除）。
- TSV 表头恒为：`时间 / 柜号 / 条码 / 操作员 / 结果`。
- 正常记录结果为「正常」；串号/重复/超量为「异常」；辅助码为「辅助」。
- 落盘文件与数据库记录一一对应，不丢码。
- 测试结束后只清理 `E2E-*` 柜号与测试型号，不碰真实数据。

### 1.4 L4：电脑端同步端到端

由于 App 的 WiFi 同步默认下线，L4 分两种模式：

- **默认模式**：只测电脑端 API 与 TSV 生成。用脚本直接向测试服务上传构造记录，验证：
  - 按 PDA 名称 / 日期 / 柜号分目录；
  - 同柜追加、删除进回收站；
  - 下载 ZIP 目录结构；
  - 启动时按数据库重建 TSV，结果列正确。
- **开启同步模式**：用测试构建把 `AppConfig.SYNC_ENABLED` 临时设为 `true`，验证真实 PDA 配对、断网补传、规则库上传/下载。此模式只在测试机执行，不进入正式包。

### 1.5 交付物与排期

- `scripts/e2e/run_pda_e2e.ps1`：PDA 本机链路。
- `scripts/e2e/run_pc_e2e.py`：电脑端 API/TSV/ZIP 链路。
- `scripts/e2e/assert_records.py`：数据库与 TSV 对账。
- `scripts/e2e/README.md`：环境准备、运行方法、清理方法。
- 预计 **2~3 人天**；建议在 v1.12 发布前完成 L3，L4 可随后补。

### 1.6 风险与约束

- 广播注入依赖 OEM 广播名/键值，换机型需同步调整。
- 测试会安装 debug/test APK，可能影响设备现有 App；执行前必须备份 `/sdcard/zhuanggui` 和电脑端 `data`。
- 同步默认下线，L4 的「真实同步」只能用测试构建，不能直接测正式包。
- 设备日期/时区错误会导致「今天」统计断言失败，脚本启动时先校验设备时间。

## 二、PDA 首页「今日看板」方案

### 2.1 目标

首页直接看到当天装柜概况，班组长不用进记录页就能发现异常；同时保持首页轻量，不影响扫码和冷启动。

### 2.2 展示内容

建议 2×2 四张卡片：

| 卡片 | 内容 | 口径 |
| --- | --- | --- |
| 今日柜数 | 当天有扫码记录的柜号数 | 排除已删除记录；同柜多天分开 |
| 正常件数 | 当天正常扫码数 | `result = OK`，排除删除 |
| 异常件数 | 串号 + 重复 + 超量 | 三类合计；辅助码单列或不入异常 |
| 辅助码 | 当天辅助码数量 | `result = AUX`，不计入正常/异常 |

卡片下方可加一行「最近异常」：显示最近 1 条异常的时间、柜号、条码、原因；没有则显示「今日无异常」。

点击卡片 → 跳转「扫码记录查看」并自动按当天筛选；点击最近异常 → 直接打开对应柜号/记录。

### 2.3 数据与性能

- 数据源：`scan_records`（当天 `scannedAt` 范围、`deletedAt IS NULL`）+ `load_containers`。
- 聚合查询放在 IO 线程，使用 `Flow`/`StateFlow` 缓存首页状态。
- 首页 `ON_RESUME` 刷新；扫码页返回时刷新；不随每枪实时订阅全表。
- 建议补 `scan_records(scannedAt)` 或组合索引（若现有索引不足），先 `EXPLAIN QUERY PLAN` 验证。
- 查询只取计数和最近 1 条异常，不加载全表。

### 2.4 界面与交互

- 位置：首页顶部「继续装柜」卡片下方，存储提示上方或下方均可；保持现有大字、浅色主题。
- 空状态：当天无记录时显示「今日还没有扫码记录」。
- 数字格式：千位分隔；异常数 >0 时用红色强调。
- 窄屏/小屏：2×2 可改为 2 列自适应；不增加横向滚动。

### 2.5 验收标准

- 看板数字与记录页按日统计逐项一致。
- 扫码 10 枪后返回首页，数字在 1 秒内更新。
- 删除/撤回后数字同步变化。
- 跨天 00:00 后自动切到新一天，不继承昨天。
- 首页冷启动不增加明显卡顿（目标 <300ms 额外耗时）。

### 2.6 排期与风险

- 预计 **0.5~1 人天**（DAO 聚合 + 首页卡片 + 跳转筛选）。
- 风险：设备日期/时区不正确导致口径偏差；已删除记录必须排除；辅助码不能算异常。

## 三、电脑端自动备份方案

### 3.1 目标

每天自动备份电脑端 `data` 目录，防止硬盘故障、误删、误清空；支持手动备份和可验证的恢复流程。PDA 本机数据仍以 `/sdcard/zhuanggui` 为准，电脑端备份不替代 PDA 落盘。

### 3.2 备份范围

```
data/
  sync.db                 ← 记录/设备/规则库快照（最终以数据库为准）
  装柜记录/               ← 各 PDA TSV
  回收站/                 ← 删除/撤回 TSV
  规则库/                 ← 规则库备份/导出（如有）
  meta/                   ← 配对、版本等（如有）
```

不备份 `backups/` 自身，避免递归。

### 3.3 实现方式

- 服务启动后启动一个后台线程，按本地时间每天固定时刻（默认 02:00）执行。
- 备份前对 SQLite 执行 `PRAGMA wal_checkpoint(FULL)`，再用 `sqlite3.Connection.backup()` 生成一致性副本，避免直接复制正在写入的 db。
- 将 `data` 下需要备份的内容复制到临时目录，压缩为：
  ```
  data/backups/2026-10-26_020000.zip
  ```
- 先写 `.tmp`，完成后原子改名；失败保留日志，不产生半截包。
- 保留策略：默认保留最近 **30 天**，超期自动删除最旧备份；磁盘剩余空间不足时跳过并记录日志。
- 网页增加：
  - 「立即备份」按钮；
  - 备份列表（时间、大小、状态）；
  - 「下载备份」；
  - 「打开备份目录」。
- 所有操作写 `data/backups/backup.log`。

### 3.4 恢复流程

1. 停止装柜同步服务。
2. 把现有 `data` 改名为 `data_before_restore_日期`。
3. 解压目标备份到 `data`。
4. 启动服务，检查设备数、记录数、规则库、TSV 重建结果。
5. 确认无误后再删除旧目录；恢复前同样先备份当前数据。

### 3.5 验收标准

- 手动点「立即备份」→ 生成 zip，大小合理，可解压。
- 自动备份在设定时间执行一次，日志有记录。
- 备份期间继续扫码/同步不报错。
- 恢复演练：在临时目录还原后，服务能启动，记录数/规则库与备份前一致。
- 保留 30 天后旧包自动清理，不删最新包。

### 3.6 排期与风险

- 预计 **0.5~1 人天**（后台线程 + SQLite 一致性备份 + 网页按钮 + 恢复文档）。
- 风险：服务被关闭时不会自动备份（需现场保持服务运行）；备份盘空间不足；恢复必须先停服务。
- 建议默认开启，但保留配置开关 `BACKUP_ENABLED`，现场可关闭。

## 四、实施优先级建议

1. **PDA 今日看板**（0.5~1 天）：现场收益直接，改动小，先做。
2. **电脑端自动备份**（0.5~1 天）：数据安全收益高，独立于 App。
3. **端到端自动化**（2~3 天）：质量保障，建议与下一版功能一起排期。

> 三项均不改变现有扫码判定和 TSV 五列格式；开发前先单独建版本、单独提交、真机/本机验证后再推送。
